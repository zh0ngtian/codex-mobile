# 模型与 Fast 设置持久化修复

## 现象与原因

真机会话 `01a10802-a354-79a2-a553-7977e1fa3bd9` 的 rollout 证明：线程先成功以 `low` 运行，重新进入后又有一轮被客户端用新对话默认的 `gpt-5.6-sol + xhigh` 覆盖。当前实现让新对话默认值和当前线程有效设置共用同一组 React state；设置选择只改内存，已有线程直到下一次 `turn/start` 才写回，正常速度又因 `null` 被条件展开省略而无法明确清除 Fast。

## 目标行为

- 新对话的模型、智能和速度按后端保存在本机，冷启动后优先恢复；已失效的模型或选项回退到服务端配置。
- 打开已有线程时只使用 `thread/resume` 返回的线程设置，不把新对话偏好覆盖到线程。
- 已有线程修改模型、智能或速度后立即调用 `thread/settings/update`；正常速度明确发送 `serviceTier: null`。
- 已有线程的修改不反向污染新对话默认偏好。

## 计划

1. 先写失败测试，覆盖新对话设置的按后端持久化、无效数据回退和 Fast/正常值保存。
2. 扩展端到端协议测试，覆盖已有线程立即更新、正常速度发送 `null`，以及页面重载后恢复新对话模型与 Fast。
3. 实现独立的新对话模型偏好存储；在模型目录加载后归一化并恢复。
4. 为已有线程接入 `thread/settings/update`，保持乐观 UI，并用服务端完整设置通知对账。
5. 让 `thread/start` / `turn/start` 显式携带 `serviceTier`，包括表示正常速度的 `null`。
6. 跑针对性测试、完整单测、类型检查与构建；提交并推送。
7. 构建高于固定渠道 `0.2.64` 的 APK，发布到固定局域网渠道，并在真机验证冷启动新对话偏好、线程低智能恢复和 Fast/正常切换。
